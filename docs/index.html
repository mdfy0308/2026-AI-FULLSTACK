PROJECT

SBerp · Spring Breeze ERP — 사내 인사·근태 관리 시스템

어떤 서비스인가

중소기업의 흩어진 업무 데이터를 한 곳에 모으는 사내 ERP입니다.
회사·부서·사원 같은 조직 정보를 축으로 인사, 근태, 전자결재, 프로젝트, 자원 예약까지 데이터가 연결됩니다. 모든 데이터는 회사 단위로 분리되어, 여러 회사가 같은 시스템을 나눠 쓸 수 있습니다.

그중에서도 저는 인사·근태·평가·권한 영역을 맡았습니다. 사원과 직급, 권한 체계부터 출퇴근 집계와 연차 정산, 인사평가와 AI 리포트까지. 여기에 추가로 인사 규정을 답해주는 챗봇과 관리자 대시보드를 더했습니다.

  • 이메일·연락처·사번 입력 중 비동기 중복 검사
  • 직급(Position) CRUD와 권한(Permission) 체계 설정

온보딩 메일 자동화

데이터 격리

근태

출퇴근 관리

  • 출근 시각 기준 정상/지각 자동 판정 (09:00 기준)
  • 금일 중복 출근 방지 — 이미 출근 처리된 경우 차단
  • 연차·오전 반차·오후 반차 등록일에는 출근 요청 자체를 분기 처리
  • 퇴근 시 근무시간 자동 계산 (Duration 기반)
  • 관리자 전체 조회 + 본인 조회 분리

연차 관리

  • 매년 1월 1일 전사 연차 일괄 자동 부여 (@Scheduled cron)
  • 근속 연수 기반 연차 일수 산정 (근로기준법 반영)
  • 중복 부여 방지 — 서버 재시작으로 중복 실행되어도 안전
  • 연차 사용·잔여 현황 조회 (관리자 전체 / 본인 이력)
  • 회사 간 데이터 격리 — assertSameCompany 검증 일관 적용

평가

인사평가 기간 관리, AI 평가 리포트 요약

회차·평가 관리

  • 평가 기간(회차)을 6단계 상태로 관리 — 준비 → 진행 → 마감 → 생성 중 → 완료 / 실패
  • 사원별 평가 작성·제출·조회, 평가자-피평가자 관계 기반
  • 회차별 현재 상태를 관리자가 한눈에 확인

AI 리포트 배치

  • 마감 시점에 사원별 코멘트를 OpenAI API로 요약 → 리포트 자동 생성
  • @Async("reportExecutor") 전용 스레드 풀로 분리 — 트랜잭션 커밋 후 실행
  • 실패 코드 매핑 (-1: 회차 없음, -2: 허용되지 않은 상태, -3: 대상 없음)
  • 생성 실패 시 REPORTING_FAILED 상태로 전환 → 안전하게 재시도 가능
  • 프론트에서 5초 간격 폴링으로 실시간 처리 현황 표시

HR 규정 챗봇

사내 HR 규정 PDF를 근거로 답변하는 RAG 챗봇

RAG 파이프라인

  • 사내 HR 규정 PDF를 문단(Chunk) 단위로 분할하여 임베딩 벡터로 변환
  • 질문 임베딩 → 회사별 활성 규정 청크와 코사인 유사도 계산 (Java 자체 구현)
  • 상위 5개 청크를 근거 후보로 추출 (Top-K = 5)

환각 방지

  • 고정 임계값 대신 상대 유사도 기준 적용 — 1위 대비 유사도 50% 이상인 청크만 포함
  • 근거 부족 시 GPT를 호출하지 않고 고정 안내문 반환 → 불필요한 API 호출 차단
  • 근거 청크 원문 미리보기(120자)를 답변과 함께 제공 → 사용자가 출처 확인 가능

부가 기능

  • 규정 문서 관리 — 업로드·활성화·비활성화 (HrPlcyDoc)

  1. 3차

    서버와 화면의 완전 분리

    Spring Boot 4JPA + MyBatisJWTRedisNext.jsRedux-SagaOpenAI

    2026.08 – 2026.09 · 4인 서버는 화면을 만들지 않고 REST API만, 화면은 Next.js가 따로 담당합니다. 세션 대신 JWT를 사용하고 토큰은 Redis에서 관리합니다. 담당 영역에는 근태·연차와 관리자 대시보드, 인사 규정 챗봇이 새로 생겼습니다.

    정상 응답 후에도 데이터가 없을 수 있다는 걸 경험하고, 결과를 직접 확인하게 된 단계.

    주요 기능과 트러블슈팅
    주요 기능
    • 근태·연차 출퇴근 집계와 연차 자동 부여·정산. 휴가 중 퇴근 요청 같은 예외 경로까지 분기 처리.
    • 인사평가 평가 기간을 여섯 단계 상태로 관리하고, 마감 시점에 AI가 코멘트를 요약해 리포트로 생성.
    • 인사 규정 챗봇 사내 문서를 문단 단위로 나눠 질문과 대조하고, 근거가 되는 문단만 골라 답변에 포함.
    • 데이터 격리 근태·연차·평가 8개 조회 경로에 회사 식별자 검증을 일관되게 적용.
    • 구조 기존 테이블은 MyBatis에 두고 신규 영역만 JPA로. 두 방식을 엔티티로 엮지 않고 참조 컬럼만 유지.
    트러블슈팅

    연차 일괄 발생 데이터 유실

    1. 문제

      연차 일괄 발생 기능을 실행한 뒤, "2026년 연차 일괄 발생 완료, count: 87"을 반환했습니다. 예외도 없고 응답도 200이었지만, 실제 테이블에는 내용이 단 한 건도 저장되지 않았습니다.

    2. 과정

      조용히 실패하는 유형이라 로그가 도움이 되지 않았습니다. 원인으로는 세 가지 문제가 있었습니다. 배치 메서드가 같은 클래스의 개별 처리 메서드를 직접 호출해 트랜잭션 설정이 적용되지 않았고, 그 결과 저장 로직 전체가 읽기 전용 트랜잭션 안에서 실행되고, 시퀀스 채번 방식이라 저장이 지연되면서 통째로 사라졌습니다. 반복문의 카운터만 정상적으로 올라가 마치 기능이 성공한 것처럼 보였습니다.

    3. 해결

      검증이 필요한 공개 메서드와 내부 처리 코어를 분리하고, 코어를 private으로 내려 "여기는 트랜잭션이 적용되지 않는다"는 것이 드러나게 했습니다. 실제 트랜잭션 경계는 배치 메서드로 옮겼습니다.

    4. 결과

      저장 건수를 직접 조회해 확인했습니다. 이후 배치 루프에서 부르는 메서드는 private으로 두는 습관을 들였습니다.

  2. 2차

    프레임워크 전환과 외부 연동

    Spring Boot 3 Java 17 Thymeleaf Oracle 18c Spring Security OpenAI

    2026.07 · 14일 · 4인 1차 전체를 Spring Boot로, DB도 Oracle로 바꿨습니다. 팀 인원이 네 명으로 줄어 한 사람이 맡을 범위가 넓어졌고, 저는 인사에 더해 평가와 권한을 함께 맡았습니다. 외부 서비스를 처음 이용한 단계이기도 합니다.

    외부 API는 언제든 실패할 수 있으며, 그 실패를 다루는 것도 기능이라는 걸 배운 단계.

    주요 기능과 트러블슈팅
    주요 기능
    • 온보딩 메일 자동화 사원 등록 즉시 안내 메일, 입사 사흘 뒤 적응 확인 메일을 자동 발송. 실패 시 재확인 후 재발송.
    • AI 평가 리포트 평가 마감 시점에 사원별 코멘트를 요약. 진행 상태를 여섯 단계로 쪼개 실패를 별도로 관리.
    • 인증 전환 직접 구현한 세션 인증을 Spring Security 기반으로 교체.
    • DB 이전 MySQL에서 Oracle 18c로 옮기며 쿼리와 채번 방식을 전면 수정.
    트러블슈팅

    AI 리포트 회차 상태 설계 미스

    1. 문제

      사원이 300명을 넘으면 AI 평가 리포트 생성에 10분 이상 걸렸습니다. 그런데 요청을 보내는 순간 화면에는 "리포트 완료"가 표시됐습니다. 실제로는 아직 만들어지는 중인데 화면은 이를 표현할 단계가 없었습니다.

    2. 과정

      원인은 속도가 아니라 상태 설계였습니다. 하나의 상태값에 "리포트를 만드는 중"이라는 의도와 "리포트가 다 만들어졌다"는 결과가 함께 담겨 있어서, 화면이 무엇을 보여주든 둘 중 하나는 틀릴 수밖에 없었습니다.

    3. 해결

      생성 중과 생성 실패를 별도 상태로 분리해 여섯 단계로 세분화했습니다. 리포트 생성은 상태 변경이 확정된 뒤에 백그라운드에서 시작하도록 미뤘고, 화면은 5초마다 진행률을 물어 실제 처리 인원을 보여주도록 했습니다.

    4. 결과

      사용자가 몇 명까지 처리됐는지 실시간으로 확인할 수 있게 됐습니다. 실패가 별도 상태로 남으므로 처음부터 다시 하지 않고 재시도할 수 있습니다.

  3. 1차

    기능을 갖춘 사내 시스템 만들기

    Java Spring MVC JSP MyBatis MySQL

    2026.06 · 16일 · 6인 여덟 개 모듈을 여섯 명이 나눠 만들었습니다. 코드를 쓰기 전에 ERD와 화면 설계를 먼저 끝내는 방식으로 진행했고, 저는 사원 관리를 맡았습니다. 화면은 JSP가 서버에서 직접 그렸고 인증은 세션으로 처리했습니다.

    화면을 만들기 전에 설계를 먼저 끝내야 하는 이유를 알게 된 단계.

    주요 기능과 트러블슈팅
    주요 기능
    • 사원 관리 등록·조회·수정·삭제와 상세 조회, 비밀번호 초기화와 권한 수정.
    • 실시간 중복 검사 이메일·연락처·사번을 입력하는 동안 비동기로 중복 여부를 확인.
    • 멀티 테넌시 기반 설계 모든 테이블을 회사 식별자로 묶는 구조를 이때 처음 잡음.
    트러블슈팅

    조건 없는 검색으로 전사 조회?

    1. 문제

      사원 검색에서 조건을 하나도 입력하지 않은 상태에서도, 목록을 클릭하면 회사 전체 사원 명단이 그대로 나왔습니다. 이건 의도한 동작이 아니었습니다.

    2. 과정

      화면 문제로 보였지만 원인은 동적 쿼리 구조였습니다. 조건절이 회사 식별자 하나로 시작하도록 짜여 있어서, 사용자가 아무 조건도 넣지 않으면 그 하나만 남아 전체 조회가 되는 형태였습니다.

    3. 해결

      조건이 하나라도 있는지 먼저 판별해 없으면 조회 자체를 막았습니다. 그리고 수정 쿼리를 다시 보니 주소창의 사원 번호만 바꾸면 다른 데이터를 건드릴 수 있는 상태여서, 여기에도 같은 회사인 경우에만 조회할 수 있도록 where에 추가적으로 comId 조건을 걸었습니다.

    4. 결과

      이후 조회와 수정 쿼리를 새로 짤 때 회사 조건이 들어갔는지 먼저 확인하게 됐습니다. 3차에서 8개 경로의 같은 문제를 찾아낸 것도 이 습관에서 나왔습니다.
